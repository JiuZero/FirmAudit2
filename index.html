为什么要有它

做固件审计的人，都被这四件事磨过

binwalk、FirmAE、radare2、QEMU 都在，可它们之间那段路全靠人肉走。

工具齐全，链路断裂

解包、仿真、逆向、报告各有一堆工具，串起来仍然靠手工：换一份固件，就要重走一遍全过程。

让模型跑命令，心里发虚

它一句 apt install 就能把环境搞乱，下一次任务的结论就不再建立在同一个基线上。

复现失败，锅在人身上

它说"这里有个命令注入"，自己复现利用失败，转头追问，AI 答：是你的操作有误。结论无法自证。

挖到洞，交付再熬一晚

手抄复现步骤、整理证据、套 CNVD 模板，一晚上又没了。材料齐不齐，全靠提交前自查。

设计理念

三层约束，把"可信"变成可校验的状态

模型被允许一次性自由发挥，而质量这种东西一旦自由发挥就没法校验。 FirmAudit2 的做法是：用较长的输入，换较少但标准的输出。

01

过程约束

漏洞资料按 8 个段落逐段引导填充，每段过校验；段落表同时驱动引导提示词、提交校验与报告章节，是单一事实源。

  • 打回即回注校验失败的原因原样拼进下一次引导
  • 串行推进一次只推进队首一个漏洞，填不完不算完成
  • 投递对账超时收不到提交即判未送达，重投并留痕
02

结果约束

任务收口和交付前各设门，共四道。判据全部来自文件里读出来的痕迹，不来自模型的自我声明。

  • 收口门引导没填完，就不许判定为完成
  • 仿真硬门证据里必须同时有"起来过"和"回显过"
  • 资产证明门版本信息必须在复现头两步
  • 报告复核门正文与结构化字段逐条对账，漂移即重开
03

运行时约束

会话级隔离 + 单次工具调用级活性看护。Agent 在回合里改 /etc、装包全部成功，但写进的是这个会话私有的上层，回合结束随之销毁。

  • overlay 临时根宿主整盘与密钥不进沙箱
  • 分级处置中止回合 → 回注纪律 → 提前判失败
  • 重启可续任务状态落盘，程序重启不打断审计

结果门

四道门，每条缺口都是一行能读懂的人话

操作员不必猜平台为什么不出包——缺口名后面直接跟着原因。

门一 · 收口门

状态判定的前置条件

Agent 结束不等于任务完成。收口前先看引导进度，没填完就转入暂停中，并把待补清单写进状态字段。

Agent 已结束，但漏洞资料未填完，任务未判定为完成，已转入暂停中。待填清单：
- VULN-A（示意）：已填 2/8 段，当前缺「代码分析步骤」，等待引导续填
- VULN-B（示意）：已填 0/8 段，当前缺「漏洞信息」，等待引导续填

一小时后触发"恢复审计"，同一条漏洞接着从第 3 段填到第 8 段，前后 6 分钟。

门二 · 本地仿真验证硬门

证据只认运行时输出

静态分析做得再漂亮也只是分析。判据两条：复现步骤里有实际生效的启动命令，证据文件里同时出现"目标被起来"和"目标给出结果"两类痕迹。

本地仿真验证：证据里看不到目标被起来的痕迹（需含 qemu / FirmAE / Unicorn 启动输出
或服务 Listening 回显），请按分级方案实际启动目标并把启动命令的转录登记进证据

硬编码密钥、弱口令这类文件系统即可确证的类型走显式豁免，门不至于变成死规矩。

门三 · CNVD 资产证明门

版本信息必须在头两步

评审的第一诉求很朴素：先证明你复现的是这块固件。判据是"命令动词 + 版本载体"在前两个编号步骤内同现，拖到发 payload 之后再提就不算。

复现的首要步骤要用命令展示固件版本信息（前两步之内，起目标之前）：解包后 cat 版本文件
（如 ./rootfs/etc/version、./rootfs/etc/demo_version）或回读设备版本接口，并让输出与报告的固件版本一致

这一步 Agent 从来不会主动写——因为以前没人把它写成要求。

门四 · 报告复核门

过了门也不是一劳永逸

八段填齐只说明材料收齐。报告正文与已入库的结构化字段逐条对账：章节齐备、全链完整、正文与字段一致、可读性下限、本地仿真验证。

复核通过后报告又出现缺口：正文引用的脚本与证据段列出的文件对不上
→ 复核门自动重开（最多 2 次），不占死队列；人工确认仍是更权威的终审

交付门只报告缺口，状态变更只在一处——监视循环最容易出双写冲突的地方被刻意留空。

分段式引导

8 个段落，与交付报告章节一一对应

同一个任务里，放任自由发挥的模型会给你三段"我觉得这里有洞"的散文， 复现步骤的具体命令和数学答案一样"略略略"。换成先登记、再逐段填充、每段过校验， 报告质量就变成了可校验的状态。

  1. 漏洞信息类型 / 严重度 / 组件 / 置信度
  2. 漏洞描述不少于 30 字的成因陈述
  3. 代码分析步骤函数名 / 文件:行号 / 反汇编地址，不少于 2 步
  4. 代码位置文件路径 + 片段或行号区间
  5. 复现步骤编号命令，覆盖哈希校验→解包→资产证明→起目标→触发→回显
  6. PoC / Exp 脚本工作区相对路径，不得越界
  7. 证据文件命令转录 / 日志 / 回显，至少 1 份真实存在
  8. 修复建议与漏洞类型对应的可执行缓解

填齐之后的复现步骤，从空变成 近千字的命令级链路；「代码位置」也不再是一句"在某个服务里"，而是可核对的函数与指令序列。

段落表是三处消费的单一事实源

  • 引导提示词下发哪一段、要求写多细，由段落表决定
  • 提交校验每段的必填字段与下限，由同一条目生成
  • 报告章节章节顺序与段落一一对应，材料齐即报告齐

三处读同一张表，所以不会出现"引导要的"和"报告里有的"对不齐。

真实打回原因（一条都没加工）
  • description 不能为空且不少于 30 字（当前不足）
  • codeLocation 必填，且需至少给出片段或行号区间
  • poc 必须是工作区相对路径（不得为绝对路径或越界）
  • evidence 至少需要 1 个有效的工作区相对路径

会话级 overlay 临时根

发行版 rootfs 被所有任务共享且长期存活，Agent 的绝对路径写入会永久污染容器。现在每次会话挂自己的上层，回合结束随命名空间销毁；/workspace 绑定失败直接退出，绝不静默降级——产出一堆、平台一条收不到的逃逸我踩过。

宿主整盘不进沙箱

会执行任意命令的沙箱不暴露宿主盘、密钥与任务数据；技能与 Agent 资产以真实副本预置进发行版本体，环境指纹保证幂等与可复现。

离线工具链与镜像加速

解包、仿真、逆向、转换依赖随发行版一次性部署，vendor 包可完全离线；APT / pip / Node / npm 默认走国内源，受限网络下装完即用。

看护与断点续传

单次工具调用静默 15 分钟、会话静默 30 分钟两级阈值；处置分级为中止回合 → 回注纪律 → 提前判失败。任务状态落盘，程序重启不打断正在跑的审计。

交付形态

自包含平铺总包，评审者不需要理解目录结构

  • 一漏洞一档：材料全部平铺在包根，报告章节与段落表同源，要求填的就是报告里有的。
  • 固件保留原名随包：脚本自己定位同目录的固件包，复现步骤里的 ./<固件包名> 才指得通；副本取不到就显式失败。
  • 复现步骤到命令级：从校验哈希、出资产证明、起仿真到发请求，逐条能抄进终端。
  • 内容哈希去重：同名不同来源的等价材料不会变成包里的两份副本；缺材料连同原因一起登记。
  • 报告 md 为唯一正文：docx 由 pandoc 从它转换，不存在两份正文互相漂移。
